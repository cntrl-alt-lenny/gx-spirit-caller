## Reconstruction method

No prototypes existed for most of this function's ~15 callees. Rather
than guess, cross-referenced already-matched sibling `.c` files in the
same overlay that call the *same* helpers:

- `src/overlay004/func_ov004_021cbf84.c` and `func_ov004_021da898.c`
  gave the exact, already-verified signatures for the "stack-heavy
  sinks" `func_ov004_021ca0a4` (6-arg), `func_ov004_021cb778` (5-arg),
  `func_ov004_021cb568` (4-arg) — confirmed by `ov004_core.h`'s own
  brief-320 note naming these three as a group.
- `src/overlay008/func_ov008_021b2064.c` and
  `src/overlay010/func_ov010_021b32ac.c` use the *identical*
  `func_02006c0c` / `func_0201d47c` / `func_0201e5b8` / `Task_Invoke`
  sequence to build a small stack-resident config struct (task handle
  at `+0`, a `u16` flags field at `+0x14` built via `(flags&~0xF)|N`
  then later `|= 0x10`) — this is a shared SDK idiom, not
  ov004-specific, and fixed the struct shape without guessing.

## Bugs found and fixed (real, verified via `tools/verify.py --cc 2.0`
against the per-function delinked reference object — `_dsd_gap@` has
no entry for `complete`-marked functions, `--gap
build/eur/delinks/src/overlay004/func_ov004_021cd3b4.o` explicit)

1. **Bitfield mask-then-shift order, ×2 instances.** Writing
   `(raw >> 5) & 0x1f` (shift-then-mask) compiles to a single `asr`;
   the target wants `(raw & 0x3e0) >> 5` (mask-then-shift), which
   compiles to `and` + `asr` — two instructions, matching the target's
   own `and r0,r0,#0x3e0; asr r0,r0,#5`. Same fix needed a second time
   for a 3-bit extract: `x & 7` (one `and`) vs. the target's literal
   `lsl #29; lsr #29` pair (two shifts, zero-extending). Both are
   mathematically equivalent; mwcc picks a different instruction
   sequence for each syntactic form. Fixed by transliterating the
   literal shift-pair instead of using `&`.
2. **`-1` via `0xffff` vs. `mvn`.** Writing `*(unsigned short *)p =
   0xffff;` materializes the constant via a pool load; the target
   uses `mvn r0,#0` (compute -1, store the low half). Writing the
   literal as a signed `-1` into a `short *` target fixed this.

After these three fixes the diff dropped from the initial
`DIFF 188v196` (with several structural mismatches — wrong branch
*type*, not just wrong offset, at multiple points) to the same
`188v196` word count but now with every remaining diff line either a
register-choice difference or a pool-offset consequence of one — no
more wrong-instruction-type mismatches.

## Residual 1: "task-config field-write scheduling order" (confirmed, brief 682's own name)

The target writes the 5 fields of the stack config struct in this
exact order: `f0x10=-1`, `f0xc=0x4080`, `flags=(flags&~0xf)|9`
(read-modify-write), `f0x00=handle`, `flags|=0x10` (second
read-modify-write) — the `handle` write sits **between** the two
flags read-modify-writes, matching the struct-field write ordering
seen in this exact idiom's other users. My reconstruction's source
statements are in this same literal order, but mwcc's scheduler
independently reorders the two integer stores (`f0xc` and the
`handle` write) relative to each other — confirmed NOT a source-order
issue by two independent experiments, both giving byte-identical
output to each other (i.e., neither changed anything):

- Reordering the 5 statements to every permutation consistent with
  the data dependencies (flags must be read before its own
  read-modify-write) — the compiled instruction sequence did not
  change.
- Replacing the raw `char cmd[40]` + offset-cast field access with a
  proper `typedef struct { int handle; ...; short f10; ...; unsigned
  short flags; } Cmd` and `cmd.field` syntax — byte-identical output to
  the offset-cast version.

This is a genuine mwcc scheduling choice for independent
(non-aliasing, no-data-dependency) stores that resists both of the
standard levers available in this codebase's toolkit. Recording it
precisely (rather than a vague "reg-alloc wall") since a future lever
import may address exactly this shape.

## Residual 2: word_a register-choice CSE difference (brief 682's "one CSE difference")

In the phase-2 bit-packing block (building a 2-word VRAM descriptor
via `func_02005dac`), the target computes an intermediate `(0x81 -
fa4) & 0xff` into **r0** and keeps building on r0 throughout; my
compile puts the same intermediate in **r2**. Tried both a single
combined C expression and a fully step-by-step statement-per-asm-line
transliteration (matching the target's exact instruction granularity)
— identical compiled output both times. This single register swap
also correlates with the function needing one extra callee-saved
register overall (target pushes `{r4,r5,r6,lr}`; my compile pushes
`{r3,r4,r5,r6,lr}`, and reserves 4 fewer bytes of `sub sp` to
compensate — the two numbers trade off exactly, `3*4+88 ==
4*4+84 == 100`), but the root cause of the extra register was not
isolated further within this session's time budget.

## Why this isn't TST-vs-ANDS or the 4-register-spill class

Both of those are the project's long-standing OPEN residuals (see
`docs/research/reshape-recipes/imported-sm64ds-r3.md`'s "Negative
result" section) with **zero** matches anywhere in this function's
diff. Neither `tst`/`ands` instruction-selection nor a
`stmdb sp!,{r0,r1,r2,r3}` argument-spill pattern appears in either the
target or my draft. This function's residuals are new findings, not
recurrences of the known-open ones.
