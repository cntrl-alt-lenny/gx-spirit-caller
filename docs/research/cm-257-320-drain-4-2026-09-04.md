## Tooling: two Windows path-separator bugs found and fixed before any real attempt

`cmatch_loop.py`'s own docstring example canary command failed on this
machine with `no TU header 'src\\main\\func_...c' found` — `run_canary()`
compared a bare `str(Path.relative_to(ROOT))` (backslashes on Windows)
against `delinks.txt`'s forward-slash TU headers. The real per-candidate
path (`s_routed_complete_tu`) already had the `.as_posix()` fix with a
comment explaining exactly this; only the canary path was missed. Fixed
(commit `ffd80c7c8`), re-ran the canary against three real matched functions
(`func_0200093c`, `func_02000c44`, `func_02000c4c`) — all three ACCEPT at
100.00%, tree left clean.

Separately, `build_dossier()`'s own docstring/comment claims a missing m2c
`--context` "proceeds context-less" — the implementation didn't: this
machine has no host `gcc` on `PATH` (needed by `m2ctx.py`'s preprocess
step), and that exception escaped the outer `try`, dropping the whole
`m2c_skeleton` to `None` and turning every real candidate into a false "no
compilable source". Fixed by catching the `build_context()` failure locally
and falling back to `context=None`, matching the already-designed no-header
path (commit `831c7481f`). `tests/test_cmatch_loop.py` had two of its own
tests hit the exact same backslash-path bug as `run_canary` (their own
`rel = str(c_path.relative_to(cl.ROOT))`, not production code) — fixed the
same way (commit `c58404697`). All four fixes are narrowly scoped, single
root cause each, verified via the project's own pytest suite (3588 passed,
7 skipped, 83 subtests) plus the two previously-failing tests individually.

## Systemic finding: the raw m2c compile-probe scaffold has no struct padding

`prepare_compile_source`'s auto-scaffold (`cmatch_loop.py`) declares every
referenced `unkNN` field as a plain, sequentially-packed `int` with **no
padding for the real byte gap between them**. This produced the identical
symptom on four separate candidates this round — a compile that succeeds
(or a near-miss match) at the WRONG field offsets, because e.g. `unk14`
(real offset 0x14) and `unk2C` (real offset 0x2C) land 4 bytes apart in the
auto-generated struct instead of 0x18 bytes apart. `func_0202ae1c`'s ship
came directly from spotting and hand-fixing exactly this gap (95.89% →
100.0% from one `char _pad[N]` insertion); the same fix moved
`func_0201cab4` from 10.96% to 83.6% and `func_02032888`/`func_0203c46c`
partway. This is a real, mechanical, fixable scaffold bug — worth a real
tooling fix in a future round (derive the gap from the numeric suffix
deltas already present in the field names), not attempted here to stay in
scope for a drain round.

A second, related pattern: several `unkNN` fields referenced only via a
call syntax (`data->unkNN(args)`) are genuine function-pointer fields that
the scaffold types as plain `int`, producing a hard "call of non-function"
compile error. Declaring them as unprototyped function pointers
(`int (*unkNN)();`, matching the codebase's own convention for
unprototyped externs) fixes the compile but did not by itself close the
match gap on any of the three instances hit this round.
