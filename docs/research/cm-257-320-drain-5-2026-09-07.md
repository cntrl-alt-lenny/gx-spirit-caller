## Scope 1: the auto-scaffold padding bug (fixed first, before any candidate)

Confirmed exactly as described in the kickoff. `prepare_compile_source`
declared every referenced `unkNN` field as a sequentially-packed `int` with no
padding for the real byte gap between them — `unk0`/`unk10` compiled to a
2-field struct with `unk10` landing at byte offset 4 instead of its named
offset 0x10, a silent 12-byte gap loss.

**Canary (control 7):**

```text
BEFORE: struct M2CUnknown { int unk0; int unk10; };
AFTER:  struct M2CUnknown { int unk0; char _pad4[12]; int unk10; };
```

Fixed in [`tools/cmatch_loop.py`](../../tools/cmatch_loop.py)
`prepare_compile_source`: field offsets are now tracked (`prev_end`) and a
`char _pad<N>[gap]` is emitted whenever the gap between two referenced fields
exceeds 4 bytes. Covered by
`TestCompileDraftScaffold::test_unknown_field_gap_gets_explicit_padding` in
[`tests/test_cmatch_loop.py`](../../tests/test_cmatch_loop.py).

## Two more toolchain bugs found while draining (both blocked most of the pool)

**u32 redeclaration conflict (100% blocker for every ov002 candidate).**
`build_dossier` unconditionally prepended both `#include <nitro/types.h>`
(which `typedef`s `u32` as `unsigned long`) and the module's own core header
(`ov002_core.h`, which separately `typedef`s `u32` as `unsigned int`) —
confirmed against a real mwcc run on `func_ov002_022b0198`:
`identifier 'u32' redeclared ... was declared as: 'unsigned long' ... now
declared as: 'unsigned int'`. Checked: zero of the ~470 shipped `.c` files
that include `ov002_core.h` also include `nitro/types.h` — the two
established patterns are "core header only" or "nitro/types.h only", never
combined. Fix: when the module header already redeclares `u32`, skip
`nitro/types.h` and fall back to local `s8`/`s16`/`s32`/`s64` typedefs
instead (the codebase's own third precedent, e.g.
`func_ov002_0220a184.c`'s `typedef int s32;`). Covered by
`TestBuildDossierRegression::test_skeleton_does_not_double_declare_u32_for_ov002`.

**Mined per-player field-table access (`NAME.f_XXX` / `NAME->f_XXX`).**
`m2c`'s `--context` feeds it the module core header's mined field-bank
structs (`Ov002D016c`, `Ov002Ce288`, etc., brief 609/613), and its draft
freely emits member access on them — but those globals are only a real
`struct` under `#ifdef M2C_CONTEXT_BUILD`; a normal compile sees `extern char
NAME[]` instead (`ov002_core.h`'s own documented reason: ~20 already-shipped
TUs cast-offset into the `char[]` form). Confirmed against six-plus
independent real mwcc failures this round: `not a struct/union/class`. Fix:
`prepare_compile_source` now takes an optional `header_text` parameter
(threaded from `dossier.struct_header_text` at its call site) and rewrites
`NAME.f_XXX` / `NAME->f_XXX` into `(*(TYPE *)(NAME + 0xXXX))`, using the
field's real declared width from the header when available (defaulting to
`int`, the documented majority case, only when it can't be found) — this
matters: a narrower field read as `int` silently over-reads into its
neighbor rather than failing to compile. A third, related sub-case (`m2c`
inferring an already-named but wrong core-header struct, e.g.
`struct Ov002Self *arg0`, for a parameter the body still accesses via
`unkNN`) is fixed the same way the existing `void*`/`int` cases are: the
scaffold type wins. All three covered by dedicated tests in
`TestCompileDraftScaffold`.

## A falsified hypothesis: the `0x868` literal does not predict the P-20 wall

`grep 0x00000868` across the 132-candidate ov002 pool hit **85 of 132**
(64%) — far more than the 55-member P-20 cohort `codegen-walls.md` had
catalogued, which looked at first like an opportunity to bulk-screen most of
the pool without compiling. Verified against one member
(`func_ov002_02214738`) instead of trusting the pattern match: real compile
gave **11.11%** match, `diff_count=64` of 71 words, diverging from word 2 —
nothing like P-20's documented signature (~87.9%, 4 diff words, everything
else byte-identical). A second real attempt with the control-flow
restructured (`switch`→`if`/`else if`, matching the target's actual
`cmp`/`beq` chain) only reached 25.35%. **The `0x868` stride constant is
common across ov002 because of the per-player struct layout, not because
every function that touches it hits the P-20 register-swap wall** — it marks
"this function indexes per-player data," not "this function is P-20." Do not
bulk-screen on this literal in a future round; each candidate still needs an
individual read or attempt. No P-20 members were newly confirmed or screened
this round (cumulative P-20 encounters unchanged from the kickoff's stated
18).

## The ship

`func_ov002_02256ac8` (272 B, ov002) — a per-player guard-chain loop scanning
up to 5 slots per player, 2 players, checking two flag fields before firing a
callback. First real compile (after the mined-field fix) landed at **95.59%**
(3/68 words differing). Root-caused from the diff, not guessed:

- Word 17 (`e5990038` vs `e1d903b8`): mine emitted a full-word `ldr` at
  offset 0x38, target used `ldrh` — the `unk38` field is `u16`, not `int`
  (my own hand-override had guessed `int`).
- Words 21/22: identical two instructions, swapped order — traced to
  `(temp_r1 >> 2) | (temp_r1 >> 1)` vs the target's `(temp_r1 >> 1) |
  (temp_r1 >> 2)`; swapping the OR operand order matched.

Both fixed, re-verified directly via `fastmatch.match_one` before shipping:
**100.0%, diff_count=0**. Shipped through `batch_sha1.py` (dry-run then
real), confirmed via a full `ninja sha1` — see the gate section.

**Tooling near-miss along the way:** `batch_sha1.py` failed once with `ninja:
error: '...func_ov002_02256ac8.s', ... missing and no known rule to make it`
— a stale `build.ninja` graph left over from an earlier probe (this session's
own repeated `TemporaryGap`/`displace_sibling_s` cycles), not a real
byte-mismatch or a bug in `batch_sha1.py` itself. `python tools/configure.py
eur` regenerated a correct graph and the same ship command succeeded
immediately after — noted here since the error message's own diagnosis
("stray .c/.s pair") wasn't quite what was happening; the fix it recommends
(re-run `configure.py`) was right regardless.
