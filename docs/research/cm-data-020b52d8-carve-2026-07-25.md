# cm-data-020b52d8-carve: unifying the split 145-record table (2026-07-25)

Executes the deferred #1 finding from cm-data-inference-probe: `data_020b52d8`
was the strongest structural-inference evidence of that whole probe (4
independently matched, disassembly-verified consumer functions, each
confirming one field of a 12-byte record) but was deliberately NOT
retyped because it isn't the array's true base — it's a dsd sub-symbol
8 bytes into record 0.

## The split

dsd splits one physical table into one symbol per distinct address some
reader's literal pool happens to load. Four different functions each
load a pointer to a different FIELD offset within the same record, so
dsd emitted four sub-symbols for what is really one 1740-byte
(145 × 12) array:

| Symbol | Range | Prior status |
|---|---|---|
| `data_020b52d0` | 0x020b52d0–0x020b52d4 (4B) | **No source file** — sitting in dsd's implicit unclaimed-gap filler |
| `data_020b52d4` | 0x020b52d4–0x020b52d6 (2B) | `.s`, part of a brief-121 Pattern-2 worked example (2 embedded symbols in one 4-byte TU) |
| `data_020b52d6` | 0x020b52d6–0x020b52d8 (2B) | embedded in the same `.s` as above, no separate file |
| `data_020b52d8` | 0x020b52d8–0x020b599c (1732B) | `.c`, opaque `const unsigned char[1732]` blob |

## The fix

1. Extracted the 4 missing bytes at `0x020b52d0` from
   `extract/eur/arm9/arm9.bin` (reused `emit_data_blob.py`'s own
   ground-truth-byte-reading path rather than duplicating it) — this
   plus the already-shipped 1736 bytes gives all 1740 bytes of the
   table in one place.
2. Parsed all 145 records against the field layout the 4 matched
   consumers had already proven (offsets 0/4/6/8, widths int/u16/u16/u16)
   plus one unevidenced `field4` at offset 10 (no consumer reads it,
   but the 12-byte stride requires it structurally — 4+2+2+2+2=12,
   no padding needed since every field is naturally aligned).
3. Wrote `src/main/data_020b52d0.c`: one `typedef struct` + one
   `const Record020b52d0 data_020b52d0[145]` initializer, generated
   from the extracted bytes via script (not hand-transcribed, same
   discipline as the cm-data-canary tables).
4. `delinks.txt`: replaced the `data_020b52d4.s` + `data_020b52d8.c`
   entries with one `data_020b52d0.c` entry spanning
   `0x020b52d0`–`0x020b599c` (absorbing the previously-implicit
   4-byte gap into the new TU's explicit range).
5. `symbols.txt`: removed the now-unused `data_020b52d4`/`020b52d6`/
   `020b52d8` entries (no longer separately linker-visible — a single
   C array only emits one symbol at its base); kept `data_020b52d0`
   and the unrelated boundary marker `data_020b599c`.
6. Deleted `data_020b52d4.s` and `data_020b52d8.c`.
7. Rewrote all 4 consumers (`func_020119dc`, `func_020119f4`,
   `func_02011a14`, `func_02011a7c`) from `*(int*)(base+idx*12)`-style
   pointer-cast arithmetic on the old sub-symbols to
   `data_020b52d0[idx].fieldN` struct-member access on the unified
   array. Necessarily done in the same step as the delinks/symbols
   change — the old sub-symbol names stop existing, so the old and new
   forms can't coexist even transiently.

## Verification (the real risk in this item)

The doc that deferred this work flagged a real concern: struct-field
access can compile to different addressing-mode instructions than the
pointer-cast-arithmetic form it replaces (this campaign's own
[[cm-parked-reaudit-1]] item, running concurrently, is a whole
50%-hit-rate item about exactly that risk in the *other* direction —
cases where the two forms differ and only one matches). Each of the 4
consumers was checked **individually** via `fastmatch.py --gap`
against its own freshly-compiled object, not just folded into the
aggregate gate:

| Function | Field | match_percent | orig/mine words |
|---|---|---|---|
| `func_020119dc` | field0 (int) | **100.0** | 6/6 |
| `func_020119f4` | field1 (u16) | **100.0** | 8/8 |
| `func_02011a14` | field2 (u16) | **100.0** | 10/10 |
| `func_02011a7c` | field3 (u16) | **100.0** | 6/6 |

All 4 matched on the first attempt with no restructuring needed — a
direct single-field indexed load turns out to be simple enough that
mwcc's addressing-mode choice doesn't diverge between the two C forms
here (unlike the C-34/P-16 cases, which specifically involve *repeated*
access to the *same* symbol/value across multiple call-separated sites
— a single non-repeated field read has no CSE/rematerialization
decision for the compiler to make differently).

3-region `gate3.py --scope all --clean` (full pytest included, per this
item's own gate spec): see PR for the full log.

## Field semantics (not required for byte-correctness, noted for future readers)

Record 0 is all-zero (likely a null/sentinel/"no card" entry). field0
looks like a pointer into a narrow `0x020c4xxx`–`0x020c5xxx` range
(plausibly a name-string or per-record callback table elsewhere in
`main`, not yet identified) — stored as a plain `int`, not resolved to
a symbolic pointer, since the raw numeric literal is exactly as
byte-correct and carries no relocation risk. field1 increments in
loose groups (category?), field2 increments almost 1:1 with record
index (ID, with some gaps — 144 real records span field2 values 1–153).
field3 is a small varying value (stat?) with no evidenced consumer.
None of this is load-bearing for the retype; noted only as a lead for
whoever eventually goes after this table's semantic meaning.
