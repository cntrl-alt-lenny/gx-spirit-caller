# cm-data-020c3198-carve: unifying the split 16-record table (2026-07-25)

Executes the deferred finding from `cm-data-inference-3`: `data_020c319c`
(92 bytes) is not its own table's true base — it's a dsd sub-symbol 4
bytes into record 0 of a 96-byte, 16-record table. Structurally
identical to the already-shipped `cm-data-020b52d8-carve` precedent,
with one real difference in the consumer that changed the implementation.

## The split

`func_02090330` (`src/main/func_02090330.s`, a GLOBAL_ASM/no-C-match
endgame TU — see its own header comment) loads a pointer to each FIELD
of the same 6-byte record separately:

```
mov r1, #0x6
mul ip, r0, r1           ; ip = idx * 6
ldr r3, _LIT0             ; r3 = &data_020c3198
ldr r2, _LIT1             ; r2 = &data_020c319a
ldr r1, _LIT2             ; r1 = &data_020c319c
ldrh r5, [r3, ip]         ; field0 = *(u16*)(data_020c3198 + idx*6)
ldrh r4, [r2, ip]         ; field1 = *(u16*)(data_020c319a + idx*6)
ldrh lr, [r1, ip]         ; field2 = *(u16*)(data_020c319c + idx*6)
```

dsd emitted 3 sub-symbols for one physical table:

| Symbol | Range | Prior status |
|---|---|---|
| `data_020c3198` | 0x020c3198–0x020c319a (2B) | **No source file** — dsd's implicit unclaimed-gap filler (`_dsd_gap@main_177.o`, confirmed via `objdump -t`) |
| `data_020c319a` | 0x020c319a–0x020c319c (2B) | same gap object as above |
| `data_020c319c` | 0x020c319c–0x020c31f8 (92B) | `.c`, opaque `const unsigned char[92]` blob |

`delinks.txt` confirms the gap directly: `data_020c3188.s` ends at
`0x020c3198`, `data_020c319c.c` starts at `0x020c319c` — no entry
covers the 4 bytes between them, every other boundary in this region
is contiguous.

## Why this carve differs from the 020b52d8 precedent

020b52d8 had 4 consumers, all already-matched `.c` files using
pointer-cast arithmetic — rewriting them to `data_020b52d0[idx].fieldN`
struct access and dropping the now-unused sub-symbols from
`symbols.txt` was straightforward (nothing else referenced the old
names).

This table has exactly **one** consumer, and it's `.s`, staying `.s`
(no C match planned — GLOBAL_ASM endgame). Its 3 `.extern` +
`.word` literal-pool entries reference `data_020c3198`/`data_020c319a`/
`data_020c319c` **by name**, and a single C array only emits ONE
symbol at its base — so simply merging into
`const Record020c3198 data_020c3198[16]` and dropping the 2 sub-symbols
(as the precedent did) would leave `func_02090330.s` with 2 unresolved
externs.

**Investigated and rejected:** an assembly-level alias (`.equ`-style
`data_020c319a = data_020c3198 + 2` in a tiny companion `.s` stub, so
both an independent-symbol consumer and the merge could coexist).
Verified empirically against the real `mwasmarm` toolchain (throwaway
test case, not assumed): declaring an external base symbol then using
`alias = extern_base + offset` at file scope fails with
`Illegal relocatable expression` — mwasmarm cannot resolve an
externally-defined base plus a constant into a new exported symbol at
assemble time; that arithmetic is a linker-time relocation, not an
assembler-time constant.

**What does work, verified the same way:** `symbol+offset` used
directly at the reference site (a `.word` literal-pool entry, or
presumably an `ldr`/`str` operand), e.g. `.word data_020c3198+2`.
`objdump -r` on the resulting object shows a clean
`R_ARM_ABS32 data_020c3198+0x2` relocation — the same final linked
address as an independent `data_020c319a` symbol, just expressed as an
offset from the (now real) base symbol instead of a second name.

## The fix

1. Extracted the 4 missing bytes at `0x020c3198` from
   `extract/eur/arm9/arm9.bin` via `emit_data_blob.read_ground_truth_bytes`
   (reused, not reimplemented) — both bytes are `0x00` (record 0's
   field0/field1 are 0, consistent with the 020b52d8 precedent's own
   record 0 also being an all-zero sentinel).
2. Parsed the 4 new bytes + the existing 92 bytes (96 total) into 16
   records of `{u16 field0, field1, field2}` (6-byte stride, matching
   the disassembly exactly — field0 at offset 0, field1 at offset 2,
   field2 at offset 4 within each record).
3. Wrote `src/main/data_020c3198.c`: one `typedef struct` + one
   `const Record020c3198 data_020c3198[16]` initializer, generated from
   the extracted+parsed bytes via script (not hand-transcribed).
4. `delinks.txt`: widened the existing `data_020c319c.c` entry's start
   from `0x020c319c` to `0x020c3198` and renamed it to
   `data_020c3198.c` (absorbing the previously-implicit 4-byte gap into
   this one TU's explicit range) — `audit()` (from `batch_carve.py`,
   the same function `emit_data_blob.py` itself uses) reports 0
   problems.
5. `symbols.txt`: **left `data_020c3198`/`data_020c319a`/`data_020c319c`
   completely unchanged** — same as the 020b52d8 precedent's actual
   shipped state (its own write-up said it removed the sub-symbols, but
   the current tree still has all 4; the "keep address-only markers for
   every dsd-split symbol forever" gotcha from that item's postmortem
   applies here too, so this was left alone deliberately, not by
   oversight).
6. Deleted `data_020c319c.c` (fully absorbed into `data_020c3198.c`).
7. Edited `func_02090330.s`: dropped the now-redundant `.extern
   data_020c319a` / `.extern data_020c319c` lines, changed
   `_LIT1: .word data_020c319a` → `.word data_020c3198+2` and
   `_LIT2: .word data_020c319c` → `.word data_020c3198+4`. Added a
   short header-comment note explaining why (a reader seeing `+2`/`+4`
   suffixes without context would reasonably wonder). No other line in
   the file changed — the function's own instructions are untouched.

## Verification

- **Byte-for-byte, not just "compiles clean":** extracted-ground-truth
  bytes + git-original 92 bytes, compared programmatically against the
  actual compiled `.rodata` section of the new object
  (`objdump -s -j .rodata`) — exact match across all 96 bytes.
- **Relocation targets, not just symbol names:** `objdump -r` on the
  recompiled `func_02090330.o` shows `data_020c3198`,
  `data_020c3198+0x2`, `data_020c3198+0x4` — the same 3 final linked
  addresses (`0x020c3198`/`0x9a`/`0x9c`) the original independent
  symbols resolved to, just expressed relative to the one real base
  symbol instead of 2 separate names.
- **Full 3-region gate:** `python tools/gate3.py --scope all` —
  `GATE PASS` (eur/usa/jpn all SHA1-identical to their baseroms,
  `python -m pytest -q tests`: 3017 passed, 16 skipped, 0 failed).
  Confirmed the banner's meaning against `gate3.py`'s own `verdict()`
  source (`failed` collects every region that diverges; `GATE PASS`
  only prints when that list is empty) rather than assuming a truncated
  tail of the region-by-region output implied success.

## Field semantics (not required for byte-correctness, noted for future readers)

field0 values cluster around `0x6800`–`0x6860` (26624–26720) — likely a
pointer or ID into some other `0x6800`-region table not yet identified.
field1 is usually 0 but occasionally echoes a nearby field0 value.
field2 is small (0, 32, 64) when nonzero. None of this is load-bearing
for the retype; noted only as a lead for whoever eventually goes after
this table's semantic meaning.
